- The **store half of P1 is wired** beside the load half, behind the same `-Dvitrail.elideTargetTraffic`: the chain publishes per pass which of its writes something still reads, and an attachment nothing reads comes back as a store that does not happen. The two halves have different doors on purpose - a load needs a draw that covers the whole target, a store needs only the absence of a reader - and every uncertain answer keeps the action.
- The **encoder boundary an untracked storage-image write owes is now owed to the pass that reads it**. It costs a pass's whole attachment set in both directions, and it used to be taken after every graphics `imageStore` whether or not anything read what was written: `MetalCommandEncoder` remembers the write instead and breaks the encoder where the pass that reads it is built. Both sides default to today's behaviour - the backend answers "may read" for a pass nobody described, and Vitrail states the fact only under `-Dvitrail.narrowStorageBoundary`, conservatively, as "may read" unless the pass declares no writable image of its own and samples no name any program of the chain uses for one.
- The GPU trace P0 asked for is taken, and it answers the two questions the probe cannot. Three `Metal System Trace` recordings read through `xctrace export`: 28 s over two switches, 14 s of steady play, 14 s over a third. **Steady play is GPU-bound without a gap** - 13.65 s of shader-core activity in a 14.04 s window, 97.3 per cent, every second of it between 0.99 and 1.03 - split `Fragment 12.63 s`, `Vertex 2.02 s`, `Compute 2.03 s`, so P1's premise is hardware and not reasoning: GPU work removed is frame time returned, and the attachment loads and stores are fragment work. **A pack switch is four seconds in which the client submits no frame at all**, three of them with literally nothing submitted and the GPU at six to seven per cent. **That stall is the world being rebuilt, not the shaders being compiled**: the block-id table moves from 23877 states to 32194 and every section is built again, the switch's own report gives 178 ms of translation and 222 ms over 332 modules with none built, and the driver's shader compiler is idle throughout, having done its 3.69 s in the four seconds before the switch. The same switch took **one second** in the 02:23 session and **five** in the 02:41 one with identical compile figures, so the variable is the rebuild.

- Per-pass GPU time is **not** reachable from a Metal trace, and that is a property of the trace rather than of this engine: the GPU intervals are keyed by driver objects that intersect none of 80986 labelled objects and none of the encoders, the encoder table carries CPU-side `Encoding` events only, there is one command buffer a frame, and joining GPU intervals to encoders by time overlap leaves 100983 of 117988 unattributed. The pass names *are* in the trace - `MetalCommandEncoder.java:435` pushes a debug group named by `descriptor.label()`, the label `PassTimings` reads - but `xctrace export` does not carry debug groups. P1 does not need them: `MetalFrameProbe`'s `loadedMiB` and `storedMiB` are the quantity P1 moves - though the first measurement of those two says the reasoning that followed from this trace was wrong in one step, because the GPU is saturated on fragment work and not on attachment traffic: see the measured bullet below. Pushed debug groups would still be the way to attribute the fragment work itself.
- P1's **load and store halves are both written and off by default**. With `-Dvitrail.elideTargetTraffic=true`, `PackPass` hands the descriptor a clear where it used to hand it a null, for a target the pass is about to write every pixel of: emptying a target is a tile fill where loading it is its bytes read back off the device, and the public descriptor already expresses clear-or-load, so this needed no capability across the seam. `writesEveryPixelOfTheArea` holds three answers together - the fragment stage cannot leave a pixel as it was (`discard`, the pass's own text), no sampler of the program names a target this pass writes on the same half (read off `sampled()` joined to the plan's bindings, the question `GeometryProgram` already answers for its own attachments), and the draw is the whole screen, which is what keeps the other two honest. A clear the frame already owes is never replaced: it is owed for a reason the pass cannot see, so the emptying reaches the descriptor through `ColorTargets.takeClearOrEmpty` beside `takeClear`. The property is the switch because a wrong load action is a wrong picture rather than a slower frame; the default flips only after one session with it on has been measured against one with it off, image for image and on `loadedMiB`. Three contracts pinned the old single line as their anchor (`test_gbuffer_attachment_location`, `test_gbuffer_clear`, `test_gbuffer_write`) and were updated to the shape that carries the decision, each keeping the ordering it was written for. **Both halves are now wired**: the same switch also hands the backend the chain's answer to whether anything reads what a pass leaves, and a `false` there becomes a store that does not happen. What is owed is one session with the switch on against one with it off, image for image and on `MetalFrameProbe`'s `loadedMiB` and `storedMiB`.
- **The first pack window is measured, by a harness rather than by hand, and what it measured is that P1's load half buys no frame time.** `metallum/tools/run-vitrail-performance.sh` stages a pack and the options file beside it, writes the pack selection and the Metal preference that the settings UI would have written, launches the dev client into a world with `--quickPlaySingleplayer`, waits for the pack's own first full frame, arms the probe only then, waits out its window, collects the log and a picture and stops the client; `tools/vitrail-performance-compare.py` prints two runs side by side out of the probe's own line, and `tools/ci-vitrail-performance.py` pins the order that makes a window worth counting. Photon v1.3b with its owner's options, one scene, an 1800x1019 window (3600x2038 drawable), 600 frames a run: `loadedMiB` **935403 to 633137 (-32.3%, 1559 to 1055 MiB a frame)** with `storedMiB` **identical on both sides** (1122529), `encoders` 19712 to 19718, and **`windowMs` 17212.8 against 17245.5 - 28.69 ms a frame against 28.74, no change at all**. The two windows drew the same frame: viewport, scissor, texture, sampler and submit counts agree to within 0.06 per cent.
- **The premise P1 was ordered on is therefore partly falsified, and that is the largest thing this measurement changed.** The trace said the GPU was saturated, so the plan read "GPU work removed is frame time returned". The GPU is saturated; it is not saturated on attachment loads. The freed bytes were a sixth of the frame's attachment traffic and worth nothing in milliseconds, which says the frame is bound in the fragment shader - 12.63 s of the 14.04 traced seconds - and moves the phases that remove fragment work, P4's dead passes and P6's upscaling, ahead of anything that removes traffic. `docs/performance.md` carries the correction in P1 and points at it from that phase's own premise. The switch stays off by default: it costs nothing, it buys nothing here, and a change to what Metal is told still owes a picture comparison. The store half measured nothing for a reason recorded in the same place: twelve of the pack's fifteen colour targets are kept between frames, so almost every write is read by the next frame.
- **The picture half is not yet evidence, and the reason is the harness and not the engine.** macOS now allows screen capture to the harness's process, so both runs left a picture; comparing them shows 10.6 per cent of pixels differing by more than eight levels, with no corruption anywhere in either frame. The two windows drew the same work - identical store traffic, identical viewport and scissor counts - and the difference is the scene: the world's clock runs while a session is loaded, so the second run's window opens with the sun moved, its particles respawned and the idle arm in another position. A picture comparison needs a deterministic fixture, which is what "Regression, not just frame rate" already prescribes.
- The harness's first launch found a backend fault and not a pack fault. Staged without the options file beside it, a pack comes up on its own defaults, and at those defaults one program's last sampled image lands in sampler slot sixteen: Metal has sixteen sampler slots, nought to fifteen, and the direct-resource decision counted the sampled images instead of the slot the last one lands in, so the pipeline never compiled and `nothing of this pack will be drawn`. It is fixed in Metallum (`MetalCrossShaderCompiler.needsArgumentBuffers` counts the slot) and pinned by `tools/ci-argument-buffer-samplers.py`; the same default-options load now reaches the pack's first full frame with that pipeline using Metal Argument Buffers.
- **The per-pass timing report is the host clock, and the session now has one real GPU time.** `-Dvitrail.passTimings=N` prints one ranked row a pass with the game's own labels (`Vitrail shadow chunk`, `Vitrail chunk`, `Vitrail sky`, `Vitrail entity`, `Vitrail world0/deferred4` ...), which is the attribution `xctrace export` could not give because it drops debug groups, and its numbers are not the card's: `MetalCommandEncoder.writeTimestamp` and `MetalRenderPass.writeTimestamp` both fill the pool with `device.getTimestampNow()`, and `MetalDevice.getTimestampNow()` is `System.nanoTime()`. A row is therefore the CPU cost of *encoding* that pass - `PassTimings`'s own claim that "The numbers are the card's, not the clock's" is false on this backend, and `tools/ci-frame-probe.py` pins the substitution so it cannot change silently. The readings fit: the table's total is 1.188 ms in a window whose frames take 25.15 ms (4.7 per cent), the total *grows* when the window shrinks while the frame gets faster, and the top row changes with it - all CPU encoding, none of it GPU execution. Apple's API for the real thing is a counter sample buffer (`sampleCounters(sampleBuffer:sampleIndex:barrier:)`, "A barrier ensures that the commands you encode before this one complete before the GPU samples the hardware counters", plus `resolveCounters`), and two things make it more than a flag flip: there is no encoder to sample on when a pass opens, so a pass's duration is its boundary minus the previous one's, and a barrier per boundary serialises the frame (which is why an armed run is not a run to compare frame rates with).
- **The probe carries the driver's own GPU time, and it validates the wall clock.** `MTLCommandBuffer.gpuMillis()` reads `GPUStartTime` and `GPUEndTime` - Apple: "the host time, in seconds, when the GPU starts command buffer execution" and its end, both "0.0 until the GPU finishes running the command buffer" - once per completed submit, behind the probe's guard so an unarmed session pays the boolean and not two messages; the probe reports the window's sum as `gpuMs` over `gpuFrames` and the comparison prints it as ms of GPU time a frame. One 600-frame window of photon v1.3b at 1800x1019 reads **25.25 ms of GPU time a frame against 25.21 ms of wall-clock** - the same number twice, which is what GPU-bound with no CPU or presentation slack looks like - while the pass table from the same session claims 1.188 ms of it. **`gpuMs` a frame is the yardstick P4 and P6 are judged on**; per-pass attribution is still owed, now with a known cause and a known design.
- **P1 is closed, on Apple's own model and not on the reasoning it opened with.** Two doc readings bound it. "Choosing a resource storage mode for Apple GPUs" says Apple GPUs "have a unified memory model in which the CPU and the GPU share system memory", that the `private` mode "defines system memory that only the GPU can access", and that only `memoryless` "defines tile memory within the GPU" - so a private render target's load and store are system-memory traffic whether the pool is unified or not, and unification removes the copy *between* pools rather than the transfer between tile memory and the pool. "Setting load and store actions" prices exactly what the phase removes (`load` "is significantly slower" than `dontCare` or `clear`; `dontCare` "incurs no cost"; the store is a decision "between render passes"; and `storeAction.dontCare` is "[t]ypically the correct action for depth and stencil render targets"), which is what makes the null result a fact about this frame rather than about the API: the frame is bound in the fragment shader, so an action on a path it is not waiting for costs nothing to remove. The depth slot is the one attachment the lifetime capability cannot reach (`MTLCommandBuffer.java:190-201` stores depth unconditionally) and it measures **444 MiB a frame, 13.0 per cent of the frame's attachment traffic** - less than the 509 MiB the load half removed for no frame time, and only a fraction of it is elidable because depth accumulates across passes. What Apple documents *above* the action level stays on the table for a memory-bound frame and is not a per-attachment flag: `memoryless` storage mode for a texture "used only within a single pass", and tile shaders, which "allow your app to compute and save data to tile memory that's persistent on the GPU between render passes" instead of storing intermediates out and loading them back. Neither applies to this pack's chain, whose targets are read across passes by construction. The switch stays off by default and the mechanism stays for P4, which consumes the same lifetime facts; what would reopen the default is a frame bound on memory rather than on the fragment shader, which is a property of the resolution and the pack.
- **The frame's GPU time is a straight line in pixels, and that is now the measured case for the upscaling phase.** The probe's `gpuMs` - the driver's own answer, `GPUStartTime` to `GPUEndTime` on a completed command buffer - was read over four window sizes of one scene: 600x339, 900x509, 1280x724 and 1800x1019 in logical points, so drawables from 0.81 to 7.34 megapixels, 600 frames each. Wall clock and GPU time agree at **every** size (never more than 0.3 per cent apart), so the frame is GPU-bound across the whole range with no CPU or presentation wall, and
  `gpu ms a frame = 6.92 + 2.726 x megapixels` (R2 = 0.9993). At 1800x1019 the 26.80 ms frame is therefore **20.00 ms that scales with pixels and 6.92 ms that does not** - geometry, shadow and compute work that no resolution change can touch. What an upscaler is worth is bounded by that and now known: 70 per cent linear scale is 16.73 ms (1.60x), 60 per cent is 14.13 ms (1.90x), 50 per cent is 11.93 ms (2.25x), before the upscale's own cost. **Measured again at a player's own window shape, where the world is much smaller than the output**: at 3600x2260 (8.14 Mpx of output) Photon v1.3b costs 29.95 ms a frame at 100 per cent (33.4 fps) and 14.31 ms at 55 per cent (69.9 fps) over 600 frames each - the world's pixels at 2.756 ms a megapixel, so 6.78 ms of the 14.31 is the world and **7.53 ms is what the slider cannot touch**, the upscale writing every output pixel plus the scene's geometry, shadow and compute. At the slider's floor of 25 per cent the same scene is about 8.9 ms (112 fps), which is the ceiling; below roughly 60 per cent more of the frame is scale-independent than scale-dependent. **The same two points on the owner's own world** (their save, window, pack and pack options, which are the fixture's byte for byte): 24.99 ms at 100 per cent and 11.14 ms at 55 per cent with the shadow map at 40 (40.1 against 89.9 fps); the shadow map's fill is 0.69 ms of that, and **halving the render distance 32 -> 16 moves 11.14 to 11.15**, so beyond the near field the extra chunks are not a per-frame cost at this pack's fog. Every one of these is GPU time; a live session with 56 mods reported 43 and 31 fps over windows containing pack reopens and had no probe line, so nothing in it says whether those frames waited on the GPU or on the CPU - `windowMs` against `gpuMs` is what tells a pack-bound frame from a mod-bound one. It also bounds the other phases: P4 can only remove work inside the 20 ms, and P1's null result is consistent, because attachment traffic is not what those 20 ms are made of. Recorded in `docs/performance.md` under P6.
- **P6's two pack-semantics decisions are recorded, and the seat it will occupy already exists.** Decided (owner-approved): MetalFX is **engine level, after the pack's final pass, off by default, never inside the pack's chain** - which is not a new seat but the one FSR 1.0 already occupies, since the scaled picture is drawn up onto the window-sized colour texture before any widget lands on it; **one upscaler, chosen deliberately** (the settings page presents one choice; Temporal Fold belongs to the FSR 1.0 side, and two upscalers in a frame is a bug with a good frame rate); and **nothing pack-visible changes**, because a pack is told `viewWidth`/`viewHeight` and MetalFX runs after the chain has finished, so changing what a pack is told stays a separate per-pack evidence decision. `docs/render-scale.md` is the doc this rests on: render scale, FSR 1.0, sharpen and Temporal Fold already exist on the Video Settings page, and the upscale is a **fixed cost** - two passes at the window's resolution that do not shrink with the slider. The measured headroom (1.60x at 70 per cent, 1.90x at 60, 2.25x at 50) was taken at `renderscale=100`, where the upscale does not run at all, so MetalFX's own fixed cost comes out of that gain and the honest comparison is against the upscaler it replaces, not against none. Acceptance: off restores today's path and image exactly, on at the same scale is not slower than what it replaced (`gpuMs`), and the picture is reviewed per pack. The first work item is to measure the FSR 1.0 seat's own `gpuMs` at a few scales so 'not slower' has a number.
- **P6's seat cost is measured, and the copy side has a named target of exactly three.** One window of 1800x1019 at four render scales gives `gpu ms a frame = 7.22 + 2.775 x megapixels drawn + 2.31 x (scale below 100)` with a residual sum of 0.077 over four points: 7.22 ms that does not scale with pixels, 2.775 ms a drawn megapixel, and **2.31 ms for the FSR 1.0 upscale plus its sharpen**, paid at the window's size whatever the slider says, which is what `docs/render-scale.md` says of it. With that upscaler already paid for, the practical gains are **1.23x at 80 per cent, 1.50x at 65, 1.90x at 50**, and 2.31 ms is the bar a replacement has to beat. Run-to-run drift on this scene is 0.5 to 0.8 ms (a moving sun), so both numbers sit clear of it.
- **P4's copy consumer is not empty: the engine already prints `10 targets are copied back from their far half at the end of every frame ... and 3 of those are read by nothing in the frame, so moving them is work nothing asked for`.** That is the declaration-versus-use gap already reduced to a list: three full-size copies at 1800x1019 are about 87 MiB read and 87 MiB written a frame, of the order of a millisecond of a 27.58 ms frame - certain, named and small. The binding side is already handled at bind time (`Samplers bound from what a module reaches`), so no reflection project is owed. **The missing reading is a blit counter**: the probe counts attachment loads and stores, encoders and bindings, and a copy-back is a blit, so the copies live inside `gpuMs` and are invisible in its decomposition.
- **P4's copy elision is written and measured, and it is correct but small.** `-Dvitrail.elideTargetCopies` (off by default) filters the end-of-frame copy-back list by the plan's own read set on the half the copy writes to. The probe gained a blit counter to see it, and the first session it ran on moved **225 MiB a frame in eleven copies** - larger than the depth attachment's loads, and never counted before. Against one session the switch removes exactly the three copies the announcement names (eleven a frame to eight, 6600 blits to 4800), and they are small ones: the window's copy traffic falls 135187 to 131441 MiB, so the three are 6.24 MiB a frame where a full-size target is 28 MiB - of the order of a twentieth of a millisecond. ## Vertex-input findings

- Iris 26.1 defines `at_midBlock` on `IrisVertexFormats.TERRAIN`, while `IrisVertexFormats.ENTITY` contains `iris_Entity`, `mc_midTexCoord` and `at_tangent` but not `at_midBlock`. Iris shader keys use `ENTITY` for ordinary entities and shadow entities.
- Vitrail keeps `EntityVertex.ANSWERED`, the three appended entity elements and entity stride unchanged. `VertexInputDiagnostics` distinguishes real mesh-backed answers from inputs that the Iris reference format also leaves without a backing vertex array; `EntityInputDiagnostics` delegates to that classifier.
- Iris 26.1 uses `DefaultVertexFormat.PARTICLE` for `PARTICLES`, `PARTICLES_TRANS` and `WEATHER`. That format carries none of `mc_Entity`, `mc_midTexCoord` or `at_tangent`; Iris's core transform path does not turn those three into real particle/weather vertex fields. Vitrail therefore keeps an empty real-answer set and classifies those names only as reference-unbacked diagnostics.
- Iris 26.1 sky keys use `POSITION`, `POSITION_COLOR`, `POSITION_TEX` or `POSITION_TEX_COLOR`. None carries `mc_Entity` or `mc_midTexCoord`. With zero entity components, `VanillaCoreTransformer` leaves pack-declared `mc_Entity` unbacked; an explicit `mc_midTexCoord` likewise does not become a physical sky element. Vitrail classifies both as reference-unbacked for sky diagnostics without changing any sky format.
- Iris 26.1 `LINES` uses `DefaultVertexFormat.POSITION_COLOR_NORMAL_LINE_WIDTH`, which carries neither an entity id nor UV2. `VanillaCoreTransformer` renames `vaUV2` to an `iris_UV2` input even when `hasLight()` is false, while no UV2 element backs that input; zero entity components likewise leave pack-declared `mc_Entity` without backing data. Vitrail classifies both as reference-unbacked for line diagnostics while leaving `LinesVertex.ANSWERED` and the line ABI unchanged.
- These reference-unbacked classifications do **not** claim value-for-value parity with OpenGL generic-attribute state on every draw. Vitrail continues to supply its existing deterministic synthesized constants; no constant value changed in this diagnostic work.

## Sky ownership / scene-seed finding

- The scene seed cuts itself only against the depth-valued coverage texture. Geometry coverage is normally written by the translated fragment epilogue after the pack's fragment `main`, so a pack-authored `discard` prevents that write.
- That fragment-survival rule is correct for terrain, entities and other ordinary geometry: a discarded fragment is a pixel the pass did not cover. It is not sufficient for the sky elements whose mesh metadata says `covers=true`. Those elements mean the pack owns every pixel the mesh spans; under the reference renderer a discarded pack fragment does not cause the vanilla sky shader to be drawn there afterwards.
- The fix is Vitrail-only and sky-only. A claimed sky draw is replayed through a second pipeline that reuses the exact translated pack vertex stage and the same bound vertex buffer, but writes only `gl_FragCoord.z` into the existing coverage attachment. The pack fragment stage is not run on this replay, so its colour writes and discards cannot change the ownership answer.
- The replay uses the pack vertex stage rather than vanilla placement because a pack may change `gl_Position`; the claim must rasterize the same pixels as the sky it belongs to. The horizon cone is replayed immediately after its own ordinary draw while its vertex buffer is still bound.
- The coverage value remains a depth rather than a boolean. `SceneSeed` can therefore still carry a game feature whose live depth stands in front of the claimed sky. No terrain/entity/particle/hand coverage path is changed.
- The ownership sibling is prepared only when the ordinary sky program really has a coverage attachment. A device/compiler refusal of the sibling leaves the existing fragment-written coverage in place and is diagnostic rather than disabling the pack sky.
- Minecraft 26.2 records the top/dark discs and sunrise with direct `draw`, while sun, moon, stars, End sky and End flash use `drawIndexed`. Ownership replay mirrors that split with strict injector counts (2 direct targets for the non-main-disc hook, 5 indexed targets) and repeats the exact indexed arguments while leaving the game's bound index buffer standing.
- The observed `gbuffers_skybasic` programs add a second edge case: they declare zero pack colour outputs. The translator previously refused coverage solely because `maxFragmentOutput` was `-1`, so the ownership sibling had no attachment to write. Zero-output coverage is now legal at colour rank 0; `GeometryProgram` omits the inert default colortex attachment in that shape, leaving the single slot for the coverage texture. The ordinary fragment still obeys `discard`; only the sky sibling turns semantic ownership into a mark afterwards.
- The ownership replay is now source/CI plus real-device structural evidence on Solas and Photon at `ac33fed3 + 82a0c75e`: the former sibling attachment mismatch is gone and the zero-output coverage-only `gbuffers_skybasic` path compiles and draws. Bliss remains the primary visual acceptance case because this run did not load it; no Bliss name or pack-specific branch is used by the fix.
